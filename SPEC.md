# Техническое задание: Entropy Money v2

> Самодостаточный документ. Не требует доступа к переписке, в ходе которой он составлен.

## 1. Назначение и цель

Entropy Money v2 — консольная (CLI) система **партнёрских взаимозачётов на подписанных контрактах (IOU / mutual credit)**. Участники выпускают, подписывают и погашают долговые обязательства, обмениваясь ими в виде подписанных файлов-пакетов. Система ведёт локальный **реестр (ledger)**, из которого вычисляются балансы, умеет **аудировать** целостность реестра и **визуализировать граф долгов**.

Проект является переработкой старого прототипа `entry`/`entropy` (cli `entropy`, «Entropy Money», 2019): от исходного кода сохраняется только предметная идея (подписанные денежные контракты на Ed25519), вся реализация переписывается с нуля.

## 2. Что проект НЕ делает (рамки)

- Это **не блокчейн**, нет майнинга, консенсуса, токенов и «цепочки блоков».
- Нет P2P-сети и онлайн-обмена между узлами: обмен происходит **через явный экспорт/импорт файлов**.
- Нет центрального сервера и единой глобальной базы.
- Приложение не хранит деньги и не имеет выхода в реальные платёжные системы.

## 3. Глоссарий

- **Участник** — владелец пары ключей Ed25519.
- **Адрес** — идентификатор участника, производный от публичного ключа.
- **Алиас** — человекочитаемое имя участника (локальное / передаваемое в пакете).
- **Контракт** — подписанное обязательство (IOU/TRANSFER/SETTLE).
- **Реестр (ledger)** — множество принятых (валидных) контрактов; источник истины.
- **Баланс** — вычисляемая проекция реестра, а не хранимое значение.
- **Пакет (bundle)** — переносимый файл с контрактами (+ алиасы) для экспорта/импорта.

## 4. Технологический стек

- **Язык:** Go (актуальная стабильная версия), **Go Modules**.
- **Криптография:** стандартная библиотека `crypto/ed25519` (НЕ устаревший `golang.org/x/crypto/ed25519`).
- **CLI:** `github.com/spf13/cobra` (сохраняем, доводим дерево команд до финала).
- **Хранилище:** встроенная БД `go.etcd.io/bbolt` (один файл, чистый Go).
- **Шифрование ключей:** `golang.org/x/crypto/argon2` (Argon2id) + `crypto/aes` AES-256-GCM.
- **Адреса:** base58 (например, `github.com/mr-tron/base58`).
- **Графы:** вывод в Mermaid и DOT (генерация текста, без внешних сервисов).
- **Тесты/CI:** `go test`, `go vet`, `gofmt`, `golangci-lint`, GitHub Actions.

## 5. Участники, ключи, адреса, алиасы

1. Приватный ключ генерируется командой и **шифруется паролем (passphrase)**; в открытом виде на диск не пишется.
2. Ключи хранятся в каталоге `~/.entropy/` (имя/путь настраивается флагом).
3. Приватный ключ шифруется схемой **Argon2id (KDF от пароля) + AES-256-GCM**; для любой операции с подписью пароль запрашивается.
4. Участник идентифицируется **адресом**, производным от публичного ключа (хеш публичного ключа в base58). Пример формата: `ed25519:<base58-hash>`.
5. Поддерживаются **человекочитаемые алиасы**: `entropy id set --name alice`, `entropy id list`. Алиас связывается с адресом; алиасы могут переноситься в пакете.
6. Права файлов с ключами — минимально необходимые (0600 для приватного).

## 6. Модель данных

### 6.1 Контракт

Обязательные поля (JSON):

| Поле | Тип | Описание |
|------|-----|----------|
| `version` | int | Версия формата контракта |
| `id` | string | Уникальный идентификатор контракта |
| `type` | enum | `IOU` \| `TRANSFER` \| `SETTLE` |
| `from` | string | Адрес плательщика/должника |
| `to` | string | Адрес получателя/кредитора |
| `amount` | int64 | Сумма в **минорных (целых) единицах** |
| `currency` | string | `USD` \| `EUR` \| `RUR` \| `GLD` \| `SLV` \| `OIL` |
| `issued_at` | int64 | Время выпуска (Unix UTC) |
| `expires_at` | int64 | Срок действия (Unix UTC) |
| `status` | enum | `draft` \| `signed` \| `settled` \| `expired` |
| `signatures` | []Signature | Цепочка подписей |
| `memo` | string | Необязательная заметка |

`Signature` = `{ signer: <address>, alg: "ed25519", value: <hex>, signed_at: <unix> }`.

### 6.2 Типы контрактов

- **IOU** — долговая расписка: `from` обязуется вернуть `amount` в валюте `currency` в пользу `to` до `expires_at`.
- **TRANSFER** — перевод кредита от `from` к `to`.
- **SETTLE** — погашение/взаимозачёт долга между `from` и `to`.

### 6.3 Денежные суммы

Суммы — только **целые числа в минорных единицах** (например, центы/копейки). Одинарной точности `float64` для денег **не использовать** (это была ошибка прототипа). Каждая валюта имеет собственный масштаб (число знаков после запятой); сумма отображается с учётом масштаба.

## 7. Экономическая модель

1. Модель — **взаимный кредит (mutual credit) без предустановленных лимитов**.
2. Баланс участника **может уходить в минус** (отрицательный баланс = участник должен системе/контрагентам).
3. Ограничений на величину и знак баланса нет: риск берёт на себя сторона, которая **ставит свою подпись** под контрактом. Подпись = согласие с обязательством.
4. Баланс **не хранится** отдельным полем. Он **вычисляется** как проекция реестра (сумма валидных контрактов по каждому участнику).
5. Реестр — единственный источник истины.

## 8. Жизненный цикл контракта

1. **draft** — контракт создан отправителем.
2. **signed** — контракт получил **встречную подпись получателя**. Только с этого момента он считается вступившим в силу и попадает в реестр как действующий.
3. **settled** — обязательство погашено (контракт типа `SETTLE` подписан обеими сторонами).
4. **expired** — истёк `expires_at`, обязательство не было погашено (вычисляется на лету от текущего времени).

Подписи образуют **цепочку**: отправитель подписывает канонические поля контракта, получатель добавляет свою подпись поверх. Для `SETTLE` подписи ставят обе стороны.

## 9. Криптография

1. Подпись — **Ed25519** (stdlib).
2. Подписывается **каноническая сериализация** контракта (детерминированный порядок полей), а не конкатенация строк, как в прототипе.
3. Проверка подписи выполняется по адресу подписанта (адрес выводится из публичного ключа).
4. Приватный ключ: Argon2id → AES-256-GCM (см. §5).

## 10. Хранилище

1. Локальная БД **bbolt**, один файл (например, `~/.entropy/ledger.db`).
2. Таблицы/бакеты: контракты, алиасы, метаданные (версия схемы).
3. **Версионирование формата** контракта и пакета (поле `version`); при импорте несовместимая версия даёт понятную ошибку, а не падение.

## 11. Обмен: export / import

1. `entropy export` формирует **единый файл-пакет** (например, `bundle.json` / `.entropy-pack`) с контрактами и алиасами.
2. `entropy import <file>` **сначала полностью проверяет** все подписи, версии и согласованность; только при успехе данные добавляются в локальный реестр.
3. Любая невалидная запись → импорт отклоняется с понятным отчётом об ошибке (что именно не сошлось).
4. Повторный импорт уже известных контрактов **идемпотентен** (не создаёт дублей).

## 12. Проверка и аудит (`verify`)

Команда `entropy verify` независимо проверяет целостность реестра и печатает отчёт:

1. Корректность всех подписей и цепочек подписей.
2. Согласованность статусов (например, `signed` есть только при наличии встречной подписи).
3. Отсутствие дублей и битых ссылок (`SETTLE` ссылается на существующие долги).
4. Непротиворечивость вычисленных балансов.
5. Итог: `OK` либо список найденных проблем.

## 13. Вывод и интерфейс CLI

1. По умолчанию — **человекочитаемый вывод** (таблицы, при возможности цвет).
2. Флаг `--json` — машиночитаемый вывод для скриптов и тестов.
3. Понятные коды возврата и сообщения об ошибках; вместо повсеместных `panic` (как в прототипе) — нормальная обработка ошибок.

## 14. Дерево команд

- `entropy key gen` — генерация пары ключей с паролем.
- `entropy id set --name <alias>` / `entropy id list` — управление алиасами.
- `entropy issue` — выпуск собственного обязательства (IOU) в пользу контрагента.
- `entropy send` — перевод кредита (TRANSFER).
- `entropy sign` — встречная подпись полученного контракта (перевод в `signed`).
- `entropy settle` — погашение долга (создание/подпись `SETTLE`).
- `entropy view` — просмотр контрактов и балансов (фильтры по типу, направлению, статусу, валюте, дате).
- `entropy verify` — аудит целостности реестра (§12).
- `entropy graph` — граф долгов в Mermaid/DOT (§15).
- `entropy export` / `entropy import` — обмен пакетами (§11).

## 15. Визуализация графа долгов

`entropy graph` строит граф «кто кому должен» и выводит его в форматах **Mermaid** и/или **DOT** (для вставки в README или рендера в Graphviz). Направленные рёбра — обязательства, подписи — узлы-участники (адрес + алиас).

## 16. Структура репозитория

```
cmd/entropy/            # точка входа
internal/crypto/        # ключи, шифрование, подписи, адреса
internal/domain/        # контракт, статусы, типы, суммы
internal/ledger/        # реестр, вычисление балансов
internal/store/         # bbolt-хранилище
internal/bundle/        # export/import пакетов
internal/verify/        # аудит реестра
internal/graph/         # Mermaid/DOT
internal/cli/           # команды Cobra
```

Черновые файлы старого прототипа (`_/b2b.go`, `_/test.go`) удаляются; полезные идеи (проверка подписи, точность сумм) переносятся в рабочий код.

## 17. Этапы работ (roadmap)

**Этап 1 — Работающее ядро**
- Переезд на Go Modules и структуру §16.
- Крипто: генерация ключей с паролем, адреса, подписи, каноническая сериализация.
- Доменная модель контракта и типы IOU/TRANSFER/SETTLE.
- Реестр на bbolt + вычисляемые балансы.
- Команды: `key gen`, `send`, `sign`, `view`, `export`, `import`.
- Unit-тесты ядра + CI (build/vet/test/fmt/lint).

**Этап 2 — Полный жизненный цикл и надёжность**
- Алиасы (`id set/list`), `issue`, `settle`.
- Полный цикл `draft → signed → settled → expired`, обработка сроков.
- `verify` (аудит реестра), `--json`, нормализация ошибок и кодов возврата.
- Расширенные тесты (негативные кейсы, импорт невалидных пакетов).

**Этап 3 — Витрина для портфолио**
- `graph` (Mermaid/DOT).
- Демо-сценарий (`make demo`): создаёт 2–3 участников, выпускает долг, подписывает, делает перевод, погашает `SETTLE`, показывает балансы и граф — весь прогон за ~30 секунд.
- README (двуязычный EN + RU), бейджи CI, описание архитектуры.

## 18. Тестирование и CI

- Unit-тесты: подписи и их проверка, валидация контрактов, вычисление балансов, идемпотентность импорта, отказ на битых подписях/версиях.
- CI (GitHub Actions): `go build`, `go vet`, `go test ./...`, проверка `gofmt`, `golangci-lint`.
- Целевые команды в `Makefile`: `build`, `test`, `lint`, `demo`.

## 19. Критерии готовности (Definition of Done)

1. Установка и запуск на чистой машине без ручных правок (только `go install` / `make build`).
2. Демо-сценарий из §17 (Этап 3) проходит целиком без ошибок.
3. `entropy verify` на демо-реестре возвращает `OK`.
4. Экспорт/импорт корректно отвергает подделанные подписи и несовместимые версии.
5. Все тесты проходят, CI «зелёный».
6. README (EN + RU) позволяет за ~5 минут понять назначение и повторить демо.
